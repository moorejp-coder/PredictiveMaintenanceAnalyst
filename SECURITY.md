# Security

PRISM is a student contest project. Every sensor reading is simulated. PRISM connects to no real machine and holds no real personal data.

## Report a problem

Email moorejp@cua.edu with the subject "PRISM security". Do not post details in a public issue. Name the page or route, the steps to repeat the problem and what you saw. This is a student project with no bug bounty, and I do not promise a reply time.

## How PRISM handles security

- Secrets: keys and passwords live in `.env` on a local copy (ignored by git) and in Elastic Beanstalk environment properties on the live site. `.env.example` holds blank placeholders only. A search of the 200 most recent commits on Oct 22, 2026 found no AWS, Anthropic or GitHub token patterns. That search is not a full audit.
- Sign-in: the live site runs with `REQUIRE_LOGIN=true`. With no `REQUIRE_LOGIN` property set, a production copy requires sign-in too (`config/prism.php`). Judges open the read-only Judge Demo and need no account. PRISM sends no invite on its own. The entrant sends an invite link only when a person asks for one. The link lets the person choose a password of at least 12 characters, works once and expires after 30 minutes. Laravel stores passwords as hashes (bcrypt, 12 rounds). A password change ends the account's other sessions.
- Record access: override entries and AI ratings have a random UUID as their public id, so a URL or API response never shows a row number. A signed-in user lists, views, edits and deletes only the entries that user logged: `GET /api/overrides`, and `GET`, `PUT` and `DELETE /api/overrides/{uuid}`. The `authorize.resource` middleware and `OverrideLogPolicy` check the owner on the server. A guest or a demo session gets 401. Another user, or an entry with no owner (logged before accounts were recorded, or with the sign-in off), gets 403. A refused request is written to the Laravel log with the user id, IP address, route and entry id. These routes have no screen in the dashboard. `tests/Feature/OverrideOwnershipTest.php`, `AuthorizeResourceTest.php` and `PublicIdTest.php` check them.
- Override log history: an edit keeps the original reason, and a delete only marks the entry deleted. The admin-only `/overrides` page shows both. For a deletion request, the admin's Erase button on `/overrides` or `php artisan prism:erase-overrides --account=<email>` removes entries for good, and the Delete button on `/admin/invites` or `php artisan prism:delete-account <email>` removes an account with its invite links and the entries it wrote (`app/Services/PersonalData.php`, `tests/Feature/PersonalDataDeletionTest.php`). Emailed set-password and unlock links carry the token and email after `#`, so neither reaches the server in the address or an access log.
- Separate passwords guard `/admin/invites` and `/overrides`. Both are checked with `hash_equals`, and both pages return 404 when no password is set.
- Rate limits: every limit lives in `app/Support/RateLimits.php` and each route counts on its own. Sign-in, set-password, unlock and sign-out-everywhere forms: 5 a minute per IP address. Opening an emailed set-password or unlock link, and sign-out: 10 a minute per IP address. Reading data (`/api/readings`, your own override entries): 100 a minute per user. Writing data (override log, AI ratings, editing or deleting your own entries): 20 a minute per user. Routes that cost money or run heavy work have their own limits. Judge invites send an email through Amazon SES: 10 an hour per admin, plus a site-wide cap of 100 emails a day (`PRISM_EMAIL_DAILY_CAP`) that also covers account lock emails. The set-password and change-password forms ask the Have I Been Pwned API: 20 an hour per IP address on top of 5 a minute. The override review page and the invite page read the most rows: 30 a minute per user. The AI diagnosis and AI work order routes call the Anthropic API, and one press of Explain this reading calls both: 10 a minute and 60 an hour per user each. AI spending is also capped in dollars from the token counts the API reports (`app/Support/AiBudget.php`): $0.05 per user per hour and $1.00 for the whole site per day by default (`PRISM_AI_USER_HOURLY_BUDGET_USD`, `PRISM_AI_DAILY_BUDGET_USD`), priced at the Claude Haiku 5.5 list prices. A spent budget answers 429 with `Retry-After`, and a call already under way stops before it costs more. `tests/Feature/ExpensiveRoutesTest.php` checks these. File uploads: 5 a minute per user (`throttle:uploads`); PRISM has no upload route today. A visitor with no account (the Judge Demo) counts by IP address. Over a limit the answer is 429 Too Many Requests with a `Retry-After` header in seconds, plus `X-RateLimit-Limit` and `X-RateLimit-Remaining`. Sign-in also blocks an IP address for 15 minutes after 5 failed sign-ins (429 with `Retry-After`) and locks an account for 30 minutes after 10 wrong passwords in a row. The owner gets an email with the time of the tries, the IP addresses and a link to change the password or unlock the account sooner. Judge invites (PRISM's only signup) allow 3 new accounts per IP address per hour and 3 set-password emails per email address per hour. A new account cannot sign in until its owner opens the emailed link, which verifies the email. The set-password link (PRISM's only password reset) gives one answer for an unknown email, a wrong token and a spent token, and 5 wrong tokens for one email in an hour, from any address, stop every try for that email for the rest of the hour. All of these answer 429 with `Retry-After`. `tests/Feature/SignupAndResetAbuseTest.php` checks them. One site-wide cap also stops the AI routes after 1,000 answers a day (`PRISM_AI_DAILY_CAP`), counting every visitor and the Judge Demo together. `tests/Feature/RateLimitTest.php` fails if an `/api/` route or a route that changes data has no named limit. `RateLimitTest`, `AccessHardeningTest`, `LoginTest` and `AccountLockoutTest` check the limits.
- Input checks: every field on every form and API route is validated on the server for type, length, range and allowed values. A JSON route answers 400 for input outside its bounds (`tests/Feature/ApiValidationTest.php`). Free text loses control characters before it is stored, and every page escapes it on output. Queries use bound values only.
- SQL injection: a review on Nov 1, 2026 checked every database query in `app`, `routes`, `database`, `config` and the scripts. No query joins user input into SQL text. Eloquent and the query builder send every value as a bound parameter, and no request value is used as a column name in `where` or `orderBy`. The only raw SQL in app code is the fixed `select 1` in `app/Http/Controllers/HealthController.php`. `tests/Unit/RawSqlGuardTest.php` fails the build when a raw SQL call (`DB::select`, `DB::statement`, `DB::unprepared`, `DB::raw`, `whereRaw`, `orderByRaw`, `selectRaw` and the other `*Raw` methods, PDO `exec` and `prepare`) gets anything other than a fixed string as its SQL, such as a variable, a `.` join or `{$x}` inside the string. The test reads PHP tokens, not text, and checks itself against samples of unsafe and safe code. It does not cover `vendor` or `tests`.
- Cross-site request forgery (CSRF): three checks guard every route that changes data. All 17 POST, PUT and DELETE routes are in Laravel's `web` group. (1) Laravel's `PreventRequestForgery` middleware requires the session's CSRF token: forms send it with `@csrf`, and the dashboard's `fetch` calls send it in the `X-CSRF-TOKEN` header. A missing or wrong token gets 419. (2) The session cookie is `SameSite=Lax`, so a browser leaves it off a POST that another site starts. PRISM sets no `XSRF-TOKEN` cookie (`app/Http/Middleware/PreventRequestForgery.php`, `tests/Feature/CookieSecurityTest.php`). (3) `app/Http/Middleware/VerifyRequestOrigin.php` (added Nov 1, 2026) refuses with 403 and logs a write request when `Sec-Fetch-Site` is `cross-site` or `same-site`, when `Origin` is not PRISM's own origin or `APP_URL` (including `null`), or, with no `Origin`, when `Referer` is a full URL on another origin. A request with none of these headers falls through to the token check. `tests/Feature/RequestOriginTest.php` checks the three layers, 11 refused header cases and that a refused request saves nothing.
- Injection audit (Nov 1, 2026): beyond SQL and CSRF, the audit checked URL parameters, file handling and shell calls. Every query string and form field is validated on the server (`scenario` from a fixed list, `tick` a whole number from 0 to 1,000,000, override ids UUIDs only). No route runs a shell command or passes input to `exec`, `shell_exec`, `system`, `proc_open` or `Process`. PRISM has no file upload: no upload field, no handler, and the local disk's `serve` option is off, so Laravel registers no `/storage/{path}` download or upload route (`tests/Feature/FileRoutesTest.php`). The judge invite email builds its link from `APP_URL`, never from the request's Host or X-Forwarded-Host header (`tests/Feature/InviteTest.php`). The file paths read by `artisan` commands come from the command line, not from the web.
- Redirects (Nov 1, 2026): every redirect goes only to a page on PRISM. `app/Support/SafeRedirect.php` is the allowlist: a path that starts with one `/`, or a full URL on the request's own origin or `APP_URL`'s origin. Anything else (another host, `//host`, a backslash, a tab or newline, `javascript:`) becomes `/`. It guards the page after sign-in (`AuthController`) and the trailing-slash redirect (`RedirectTrailingSlash`). `DropForeignReferer` removes a Referer from another site, so `back()` and the redirect after a failed form never leave the site. PRISM reads no `?redirect=` or similar parameter, and email links are built from `APP_URL`. Fixed in this review: `//evil.example/` was redirected to `//evil.example`, which a browser opens as another site. `tests/Feature/OpenRedirectTest.php` checks each redirect and 19 allowlist cases.
- Abuse screening: input that looks like an attack (script tags, SQL syntax, text over 1,000 characters) or a filled hidden `homepage` field is rejected and logged with the IP address, field, reason and the first 100 characters. Passwords and tokens are never logged. This screening is a second layer; bound queries and output escaping are the defense. A bot that posts straight to a route without the hidden field passes the honeypot. `tests/Feature/AbuseGuardTest.php` checks it.
- Audit log: `app/Support/AuditLog.php` writes one JSON line per security event to its own `audit` log channel (`config/logging.php`), apart from the application log. Every line has the event name, an outcome (`success`, `failure`, `denied` or `alert`), the UTC time to the millisecond, the signed-in account's id and whether it is an admin, the client IP address and browser type (User-Agent, with control characters removed and cut to 255 characters), the method, the path without its query string, the route name and the error reference that also appears in the application log, plus fields for that event. Events: (1) every sign-in attempt, `auth.login.success` and `auth.login.failed` with the reason (wrong password, unknown email, locked, unverified, blocked address), and also `auth.logout`, `auth.address_blocked` and `auth.account_locked`; (2) every refused request, `authz.denied` and `authz.unauthenticated`, including a policy that answers 404 so a stranger cannot tell an entry exists; (3) account changes, `account.created`, `account.password_changed` and `account.email_changed` (written from `User::booted`, so any code path that saves a user is covered, including ones added later), `account.sessions_revoked`, `account.invite_sent`, `account.deleted`, `auth.account_unlocked` and `account.role_changed`; (4) `admin.action` for every request an admin account makes to an admin page (the `audit.admin` middleware in `routes/web.php`); (5) `data.export`, `data.bulk_read` (your own override list, the admin override log, the admin account list, each with a row count) and `data.erased`; (6) `api.error_rate_exceeded` when the `/api/` routes answer with 20 errors (any 4xx or 5xx) to one IP address, or 100 to all addresses together, within 60 seconds (`config/prism.php`, `AUDIT_API_*` in `.env.example`). It alerts once per window, so a flood writes a few lines and not one per request. PRISM has no role column: an admin is an account whose verified email equals `ADMIN_EMAIL` or is in `ADMIN_EMAILS` (`User::isAdmin`), so `account.role_changed` is written when `AdminSeeder` makes an account an admin. The deploy hook runs `AdminSeeder` and `JudgeSeeder` after every deploy. Each one sets the password only for a new account or when the environment password differs from the stored one, so a deploy that changes nothing writes no `account.password_changed` line and does not end sessions. Taking admin away means changing those environment properties, and the app cannot see that. The dashboard's polling of `/api/readings` and single-entry reads are not audit events. A line never holds a password, token, session id, request body, query string or plain email address. An email appears only as the keyed one-way code from `app/Support/LogId.php`. A failure to write a line is reported to the application log and never changes the answer a visitor gets. `tests/Feature/AuditLogTest.php` checks these rules and every event except `auth.account_unlocked`, which no test covers yet.
- Security alerts (Nov 9, 2026): `app/Support/Alerts.php` and `app/Support/LoginOrigins.php` watch for eight patterns and write an `alert.*` line into the audit log: (1) more than 10 failed sign-ins for one account in 5 minutes, (2) one IP address naming more than 50 different accounts in an hour, (3) one request reading more than 100 records, or more than 10 bulk reads or exports a minute, (4) a sign-in from a new country or a new network, (5) 3 or more password links to one account in an hour, (6) 401 and 403 answers above the average of the last 24 hours. The audit line is the whole alert. PRISM sends no email or Slack message. The entrant decided on Nov 10, 2026 not to use that delivery, and the code for it was removed. The line holds counts, keyed codes and an IP address, never an email address, password or token, and each detector writes it once per subject per hour. For (4) PRISM keeps, per account, up to 20 networks as a keyed one-way code of the /24 (IPv4) or /48 (IPv6) with the first and last time and, only when a CDN header supplies it, the country, for 180 days. The settings and the off-server option are in [docs/ALERTS.md](docs/ALERTS.md). `tests/Feature/SecurityAlertsTest.php` checks each alert and each rule.
- Browser headers: a Content-Security-Policy with a per-request nonce, HSTS over HTTPS, and the other headers listed below under "Browser security headers". `tests/Feature/SecurityHeadersTest.php` checks them.
- AI: the Anthropic API key stays on the server. The AI tools only read data. PRISM has no tool that acts on a machine.
- Data kept: judge accounts (name, email, password hash), the override log (with the id of the account that logged each entry, and the original text of an edited entry), and AI answer ratings (no name, text or IP address). All of it sits in a SQLite file on the server.
- Dependencies: GitHub Dependabot alerts are on. On Oct 22, 2026 it showed 0 open and 0 closed alerts (see [docs/QUALITY.md](docs/QUALITY.md)).

## Browser security headers

`app/Http/Middleware/SecurityHeaders.php` adds browser security headers to every page Laravel serves. `tests/Feature/SecurityHeadersTest.php` checks them.

- Content-Security-Policy: all JavaScript lives in files under `public/js`, and `script-src` allows only PRISM's own origin. The views hold no inline `<script>`, and a test fails if one appears. Inline `<style>` blocks run only with a random nonce the server makes for each request. The policy allows no `unsafe-inline` or `unsafe-eval` for scripts, loads everything from PRISM's own origin, blocks plugins and blocks framing (`frame-ancestors 'none'`). The site loads no outside scripts, styles or fonts, so none are listed.
- Strict-Transport-Security (one year) and `upgrade-insecure-requests`, sent only when the request is HTTPS or `APP_URL` starts with `https://`.
- X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy and Cross-Origin-Opener-Policy. A controller that sets its own value keeps it (the set-password and unlock pages send `same-origin`: their links hold no secret in the address, and `no-referrer` would make browsers send `Origin: null` on the form, which the cross-site check refuses).
- Sessions: PRISM keeps no access or refresh tokens in the browser. Sign-in is one server-side session behind an `HttpOnly`, `SameSite=Lax` cookie, marked Secure everywhere except a local copy (`APP_ENV=local` over http), and always when `APP_URL` starts with `https://` (`SESSION_SECURE_COOKIE` overrides). PRISM sets no `XSRF-TOKEN` cookie, so the session cookie is the only cookie. A new session ID is issued at every sign-in. A session also ends when the browser (User-Agent) changes, and an IP address change is logged. The Account page (`/account`) signs the user out of every other browser after a password check. A session ends after 30 idle minutes (`SESSION_LIFETIME`) and 7 days after sign-in at most (`SESSION_MAX_DAYS`). Sign-out deletes the session on the server. The browser stores only theme, cookie-notice and judge-guide flags, never a credential.

## Known limits

- No independent security scan or penetration test has been run.
- `/overrides` and `/admin/invites` need a signed-in admin account (a verified email equal to `ADMIN_EMAIL` or listed in `ADMIN_EMAILS`). Refused attempts are logged. Every admin has full access to both pages.
- The Judge Demo needs no account and reaches the AI routes. Only the per-IP rate limits and the site-wide daily cap limit its use.
- Audit log protection: the code cannot make a log safe from someone who controls the app. Anyone who can run code as the app can change a file on the server and use the server's AWS credentials. The protection comes from where the lines are sent: a store that takes new lines and lets the server's credentials neither change nor delete old ones. This repository does not create that store, and I have not checked the AWS account settings for it, so treat the audit log as tamper-resistant only after these steps are done and checked. (a) Turn on instance log streaming to CloudWatch Logs in the Elastic Beanstalk console, set a retention period and keep the logs after the environment is terminated. (b) AWS lists the logs it streams for the PHP platform as `eb-engine.log`, `eb-hooks.log` and the nginx and httpd access and error logs. PHP's standard error is not on that list, so after a deploy, fail one sign-in and search the log group for `"event":"auth.login.failed"`. PRISM already sets `AUDIT_LOG_STACK=audit_stderr,audit_file` and `AUDIT_LOG_PATH=/var/log/prism/audit.log` (`.ebextensions/03-audit-log.config`), and `.platform/hooks/postdeploy/03_audit_log.sh` asks the CloudWatch agent to ship that file to the log group `/aws/elasticbeanstalk/<environment>/var/log/prism/audit.log`. I have not confirmed that the agent accepts this on the live platform, so run the sign-in test above and search that log group. (c) The instance role needs only `logs:CreateLogStream` and `logs:PutLogEvents` (plus the describe actions) for streaming, per the AWS documentation. Check that it has no `logs:Delete*` and no `logs:PutRetentionPolicy`, because an attacker with code execution can use the role's credentials. (d) Copy the log group to a separate S3 bucket with Object Lock in compliance mode, which AWS documents as unchangeable and undeletable by any user, the root user included, until the retention period ends. Object Lock turns on S3 Versioning. A separate AWS account for that bucket is stronger still. Sources: [Elastic Beanstalk and CloudWatch Logs](https://docs.aws.amazon.com/elasticbeanstalk/latest/dg/AWSHowTo.cloudwatchlogs.html), [S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html). An attacker who controls the app can still write false lines, so the audit log shows what was done, not that every line is true.
- Audit log and erasure: an account deletion does not edit the audit log. Editing it would let a compromised app erase its own tracks. Its lines name an account by its number and a keyed code of the email address, so after the deletion they match no one. The privacy page says so.
- Security alerts run inside the app: anyone who controls the app can switch them off, and the counters live in the cache, a file on the live site, so clearing it resets every window. An off-server path (CloudWatch metric filters and alarms on the audit log, then SNS email or Slack) is described in `docs/ALERTS.md`. It was set up on Nov 12, 2026: seven of the eight alerts have a metric filter and an alarm that emails one address through SNS. I tested the email path and a forced alarm state. I have not tested a real alert line tripping its alarm. The audit file does reach CloudWatch Logs: I saw web `auth.login.failed` lines in the log group after the deploy of that date. Since Nov 12, 2026 the instance role carries only the AWS managed policy `AWSElasticBeanstalkWebTier` and an inline policy that denies log group and log stream deletion and retention changes. A redeploy and sign-in tests passed after that change. The audit log group had no retention period set when I checked.
- Alert numbers: the limits for failed sign-ins (10 in 5 minutes), accounts per IP address (50) and records per query (100) are the entrant's. The one-hour window for accounts per IP address, 10 bulk reads a minute, 3 password links an hour and every setting of the 401 and 403 baseline (5-minute counts, 24-hour average, 3 times the average, a floor of 30, at most 20 per IP address) are my choices and have not been tuned on real traffic.
- Alert for a new country needs a CDN header (`ALERT_COUNTRY_HEADER`). PRISM does not look up where an IP address is. A visitor can send any header, so set it only when every request passes through a CDN that overwrites it. With it empty only the new-network alert runs. I have not checked whether PRISM sits behind CloudFront or Cloudflare.
- Password reset: PRISM has no self-service "forgot password" page, so alert 5 watches the password links that the admin's invite page sends. A reset page added later must call `Alerts::passwordLinkSent`.
- Data export (right of access and portability): `POST /account/export` with the password returns one JSON file built by `app/Services/PersonalDataExport.php`. Every field is picked by name. It holds the profile, every override entry the account wrote, pending invite link time, session times, and lines in `storage/logs` about the account, plus what each connected service received. It leaves out other accounts, the password hash, token hashes, session ids, the internal id and counters. IP addresses that may belong to someone else (wrong passwords, failed sign-ins) are counted, not listed, and other people's entry ids in logged paths become `{id}`. `php artisan prism:export-account <email> --output=<file>` writes the same file. `tests/Feature/PersonalDataExportTest.php` checks it.
- Account deletion (right to erasure): a signed-in user deletes their own account on `/account` with their password and a confirmation box (`POST /account/delete`). `app/Services/PersonalData.php` removes the account row, every override entry it wrote (soft-deleted ones too), its invite links, database session rows and session files signed in to it, the rate-limit and AI-spend counters keyed by it, and the lines in `storage/logs` that name it by user id or email hash (the audit log is kept apart and is not edited, see "Audit log and erasure" below). A confirmation email (`AccountDeleted`) and a receipt page list the counts. Logs kept by Elastic Beanstalk are outside the app. `tests/Feature/AccountSelfDeletionTest.php` checks each part.
- Encryption at rest: override reasons and the IP addresses of wrong passwords are encrypted with `APP_KEY` (Laravel `encrypted` casts, AES-256-CBC), and so are session files. Passwords and invite tokens are bcrypt hashes. `APP_KEY` lives in the Elastic Beanstalk environment properties, never in the repo or the database. Disk encryption (EBS) is an AWS account setting, described in [docs/DEPLOY.md](docs/DEPLOY.md). `tests/Feature/EncryptionAtRestTest.php` checks the stored values.
- Data minimization: the override form asks for no name, because the entry records the signed-in account. The invite form asks only for an email. Log lines carry a keyed hash of an email (`app/Support/LogId.php`), never the address or a plain hash. The session keeps hashes of the IP address and browser string. A text rejected only for its length is logged by length, without an excerpt. An account keeps the IP addresses of wrong passwords only until the lock email is built.
- Inline `style="..."` attributes are still allowed by the policy.
- Files nginx serves directly (CSS, fonts, images) get their headers from `.platform/nginx/conf.d/elasticbeanstalk/laravel.conf`, not from Laravel. That policy is simpler than the page policy: `style-src` allows `'unsafe-inline'`, and it has no nonce. I have not checked the headers on the live site since that file was added.
- The SQLite file has no backup. A replaced server erases judge accounts and the override log (see `docs/RECOVERY.md`).

## If you run your own copy

Never commit `.env`. Use a different password for `ADMIN_PASSWORD` and any judge account. Turn on `REQUIRE_LOGIN` only behind HTTPS.
